## 2026-08-07 — Dropped `@dicebear/core` entirely instead of migrating to v10 #decision

Dependabot PR #29 bumped `@dicebear/core`from v9 to v10, which broke the build (same failure that happened silently in the`7e3c874`bulk bump documented on 2026-07-14 and was rolled back then). v10 replaced the programmatic`StyleCreate`callback +`prng.pick()`API with a JSON-definition model where style variants are declared as individual SVG elements. STAIJA's portraits are 2 MB pre-generated SVG fragments that can't be expressed in that format, so a straightforward migration wasn't viable. Stepped back and asked what DiceBear was actually providing: the entire dependency existed to do`hash(seed) % PORTRAITS.length`. Replaced it with a 10-line djb2 hash function in `style.ts`, rewired `svg.ts`to call the new`pickPortrait(seed)`directly with a shared SVG envelope constant, removed the`vi.mock('@dicebear/core')`scaffolding from`avatar.test.ts`, dropped the `inline: ['@dicebear/core']`vitest workaround from`vite.config.ts`, and removed the dependency from `package.json`. Seed-to-portrait mapping changed (djb2 distributes differently from DiceBear's internal PRNG), but that's harmless since the seeded SVG path has zero runtime consumers (layered-avatar feature is still paused, all production UI uses slot-based PNGs via `index.ts`). Build and all 212 tests pass.

## 2026-07-14 — Pinned frontend to real `typescript@6.0.3`, not the `@typescript/typescript6` shim — TS7 blocks Vue tooling until 7.1 #decision #incident

TypeScript 7.0 (the Go-native rewrite, GA'd 2026-07-08) ships without a stable programmatic API, which `vue-tsc`/Volar need to type-check `.vue`SFCs — confirmed via [vuejs/language-tools#5381](https://github.com/vuejs/language-tools/issues/5381), blocked upstream on`microsoft/typescript-go#648`, no ETA before TS 7.1 (~October 2026 per the TS team's usual 3–4 month cadence). Microsoft's own blessed migration path — aliasing `"typescript": "npm:@typescript/typescript6@^6.0.2"`per the [TS7 announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) — looked right but doesn't actually work for`vue-tsc`: that shim's `lib/tsc.js`is a bare`require("@typescript/old/lib/tsc.js")`with no`module.exports`, and `@volar/typescript@2.4.28`(latest published, already installed) only recognizes the older`module.exports = require("./relative.js")`shim shape when source-patching`tsc.js`for its embedded-language proxy — the new two-hop`typescript6`→`old`indirection is too recent for Volar to have caught up to. Fell back to pinning`typescript`directly to the real`~6.0.3`release (the last pre-Go-rewrite version, no shim chain involved), which`vue-tsc -b`now runs against successfully.`functions/`keeps its own independent`typescript@~7.0.2`pin (separate`package.json`/`node_modules`, no Vue/Volar involvement there) and already gets the full native-compiler speedup. Revisit the frontend pin once `vue-tsc`/`@volar/typescript`ship support for TS 7.1's stable API. Side finding: with`vue-tsc`actually running for the first time this session, it surfaced 5 real pre-existing type errors in`src/services/avatar/style.ts`and`svg.ts` (`@dicebear/core`no longer exports`StyleCreate`/`createAvatar`the way this code expects) — unrelated to the TS7 work and invisible until now because`vue-tsc` was crashing before it ever reached type-checking; part of the paused layered-avatar feature.

## 2026-05-26 — Design rule: which Cloud Functions can be `onRequest`(public HTTP) vs`onCall` #decision

A function gets `onRequest` (publicly callable HTTP endpoint) only when **all four** of the following hold: (a) the caller is genuinely anonymous — no Firebase Auth session exists at call time; (b) the response is an explicit allowlist of fields, never a full doc dump, so future schema additions stay private by default; (c) any user-influenced behavior is gated on consent flags (`directoryHidden`, opt-in toggles) or one-time tokens issued by a trusted server path; (d) input is validated against a strict shape before any database read. Today the only three endpoints that meet all four are `getPublicMentors`(mentor showcase grid),`resolveReferrerName`(referral hero personalization), and`submitReferenceLetter`(referee uploads via tokenized link). All three sit behind App Check + per-endpoint validation + output-field allowlists. Anything that doesn't meet all four conditions must be`onCall`with explicit role checks — examples already in the codebase:`submitAssignment`, `gradeSubmission`, `enrollStudent`, `deleteAccount`. Adding a fourth `onRequest` endpoint should require a JOURNAL entry justifying why each of the four conditions is satisfied.
